## 一、核心发现与证据覆盖限制

## 三、踩坑复盘（按根因分类）

### A. 收口与状态一致性（Nana 本体缺陷）

**A1｜PASS 后已验证数据被改写（10-21 核心事件）**
- 触发：PRD v1.5 五轮迭代完成，05-verification PASS 落盘（10-22 09:27:07）后，主会话 SendMessage 令渲染子代理「继续修复」（01:42:37Z），子代理 a5d530fb 于 09:45:32–34 三次改写 05-artifact.json，此时 COMPLETE 与交付回复已发出。

## 四、可迁移到其他 PEV skills 的经验与适用边界

### 4.1 可直接迁移（方法层）

1. **一级证据核验模式**：背景时间线写成「历史现场（日志+mtime）」与「当前采集（哈希+命令+退出码）」两类并明确不得混用（`changes/harden-nana-pev-closeout/proposal.md:5`、verification.md 全文）。这是本轮所有 change 里最可复用的资产。
2. **先红后绿的缺口测试基座**：先固化现行行为（含反例），再把已知事故写成预期红的缺口测试，实现后转绿（verification.md:93）。任何 skill 改造都适用。
3. **provenance 三摘要绑定 + P1–P4 语义**：防「PASS 后改写」「旧 PASS 沿用」。机制可移植；但 P1 的「当前投影复算」在 evidence 语义不同的技能上会复现死锁，必须连同 lifecycle 的拆分方案一起移植（`changes/harden-nana-pev-lifecycle/proposal.md:70` 明示 rc 不能直接抄）。
4. **真人消息重放验收 + 三污染源隔离清单**：旧轮/报告/项目记忆都必须移出被测环境（C1 的教训）；六件套工具已在 `mechunit-collectors/.pev/prd-replay-2026-10-23/replay-report/` 可复用。
5. **锚定 SHA-256 + 「结构性变更才重估」条款**（rc 的做法，B3 的教训）。
6. **提案三段式**：已证实问题（每条给当前行为/证据定位/后果）→ 非问题与实验限制（防归因错误）→ 为什么每项必要、不改会怎样（lifecycle proposal 结构）。
7. **审核意见分级 + 逐条采纳/拒绝留痕**（D5 的形态）。
8. **命令面最小化判据**（四条判据、事件并入 init/commit、收口折叠）——方法论可迁移，数值不可照抄。

### 4.2 依赖 Nana 具体场景、不宜直接推广

- 模板契约（数组制、转义三分、`final_deliverable` 三级判定）是 prd 模板特有的。
- 通知夹具裁撤的前提是「终态冻结 + 事件身份幂等 + 消费守卫」三件已在；没有这三件的技能照抄裁撤等于放弃防护。
- reopen/supersede 的四条判据以 PM 轮次结构推出；其他技能事件集不同，需按同一方法论重推。
- mechunit 的真实轮次数据只能只读取证，不可改造成测试数据（多处明文约束）。
- Claude 通知竞态（迟到/重复 handback）在技能控制边界之外（v1/v2 均声明为外部限制）——其他技能不要试图在 skill 内修它。

## 六、提速建议（按优先级）与推荐流程

每条：瓶颈证据 → 调整 → 为什么可能更快 → 损失与质量守护 → 对照试验。

**S1｜验收断言前置：文档评审只审设计与判据，可执行部分全部交给脚本**（优先级最高）
- 瓶颈证据：§5.3-3，约 8h 文档往返；R1–R4 的审点多数事后转成了 P1–P4/B/C 检查与 106 个测试；实施校验抓到的 4 缺陷（排序、--pm-root）全是可测断言。
- 调整：proposal 阶段就附「验收断言清单」（夹具→期望退出码/输出），评审只对设计与判据对抗；断言由脚本在秒级跑完（101 例约 7.5 秒，verification.md:124）。
- 为什么更快：机械核对从小时级评审降为秒级脚本；评审轮次天然减少。
- 损失与守护：脚本审不了设计合理性——保留 Codex 对设计/判据的对抗审；质量以「事故夹具拒绝 + 回归绿 + 实质缺陷发现数」度量，不以「审核通过」度量。
- 试验：lifecycle 实施时双轨——先出断言清单再送审，统计审核轮次与实质发现数，对照本次 6 阶段/4 缺陷基线。

**S2｜起草与审核分职：起草方不自审，审核方不代笔**
- 瓶颈证据：01a161a9 是 Codex 自己写文档的修正轮（10.2h 跨度里往返三次语言返工）；起草=审核同体产生「基于修改前快照的误报」（X:01a166cb#L234）；反向制衡（D5）质量最高。
- 调整：change 文档由执行侧（Claude/GLM）起草并附自证核验记录；Codex 只做 1–2 次对抗终审 + 实施后校验（这两项本轮证明抓真问题，保留）。或者维持 Codex 起草，但修订轮必须换独立会话再审。
- 为什么更快：消灭「写-审-改-再审」同体循环；起草侧离日志近，核证成本本来就由它承担（b67c086e 已是事实）。
- 损失与守护：起草-实施同模型损失部分独立性——由「Codex 实施后校验」兜底（本轮该校验抓到 4 缺陷，有效）。
- 试验：harden-rc 实施由 Claude 起草实施计划+自证，Codex 仅终审一次；对照轮次/耗时/缺陷发现。

**S3｜审核意见分级 + 只复核 BLOCKING**
- 瓶颈证据：R4 内 11:32→12:50 四次往返剩余问题递减；「INIT 第 0 轮」P1 被用户一句降级（X:01a163d8#L286）——说明大量中间级意见本可不当轮处理。
- 调整：全量审一次，输出 BLOCKING/HIGH/MEDIUM；只对 BLOCKING 修复做一次复核；MEDIUM 进 tasks 跟踪、并入下一版。
- 损失与守护：MEDIUM 修复延后——BLOCKING 判据成文（影响正确性/可实施性才 BLOCKING）；MEDIUM 不许丢，进任务清单。
- 试验：同 S1 双轨统计。

**S4｜拍板批处理 + 转贴改落盘**
- 瓶颈证据：§5.3-1 与 -5（空闲占 60–80%；三次手工转贴）。
- 调整：每轮收尾只输出「待拍板清单」一次问齐（PEV 的 AskUserQuestion 已支持，892673c5 内用过）；评审意见落盘为 change 目录内 `review-log.md`，两个 CLI 都读文件，不再粘贴；低风险项（措辞/命名/排版）默认授权。
- 损失与守护：低风险项出错晚发现——授权白名单 + Codex 终审兜底。
- 试验：下一 change 记录拍板次数与两次拍板间的等待时长，对照本次十余次分散拍板。

**S5｜上下文与用量治理**
- 瓶颈证据：§5.3-2 与 -4（46 万单次 input、5 小时 429 停摆、渲染子代理 12 分钟/119K tokens）。
- 调整：阶段级新会话 + `--resume` 逐轮续（重放实验已验证可行，9 轮全成）；验证子代理输入裁剪固化为契约（三轮 100K/46K/88K 的自发裁剪已有，C:7ec63d1b#L1214）；lifecycle 的命令面 12→5 落地后直接减少模型-脚本往返；重任务避开 5 小时用量窗口尾段。
- 损失与守护：会话切换丢隐式上下文——state.json+证据账本已跨会话，重放实验证明不回退。
- 试验：lifecycle 实施后用重放六件套的 token-usage.json 同口径对比一轮。

**S6｜重放验收固化为生命周期类 change 的收口门**
- 瓶颈证据：7 轮设计评审未发现 reopen 死锁，重放一轮即暴露（§一-4）；重放成本仅 2.2h 活跃。
- 调整：凡改状态机/收口逻辑的 change，合并前必跑一次真人消息重放（工具六件套现成）；隔离照 C1 清单。
- 损失与守护：每次约 2h 成本——只对生命周期类 change 强制，其余抽查。

**S7｜方向探索不再用消融实验**（用户已拍板，此处仅固化）：消融 ~11h 活跃换回负结果；实验只用于验收（重放），不用于找方向。

### 最推荐的执行与审核流程（S1–S6 组合）

1. **立项**：执行侧起草 proposal（附已证实问题三段式 + 验收断言清单）。
2. **一次全量对抗审**：Codex 输出分级意见，落盘 `review-log.md`。
3. **用户一个拍板窗口**：只裁 BLOCKING 处置 + 待拍板清单。
4. **修订 + 脚本验收**：事故夹具拒绝、断言全绿、回归绿。
5. **Codex 终审一次**：验证修订与断言，不再逐字重审文档。
6. **实施**：Claude 单会话连续 TDD（本轮已证明 3.1h 连续可行）。
7. **Codex 实施校验**（保留，本轮抓 4 缺陷）。
8. **生命周期类 change 加跑 e2e 重放**。

预期（推断，待 S1 试验验证）：审核往返从 6 阶段约 15 次降到 3 次以内；文档打磨活跃从约 8h 降到 2–3h；用户拍板从十余次分散降为 2–3 次集中。质量验证只认四件事：实质缺陷发现数（基线：4 实装缺陷 + 4 e2e 瑕疵 + 重放 P0×2）、回归绿数、事故夹具拒绝、返工轮次——不以「审核通过」或「轮次减少」单独代表质量提高。
