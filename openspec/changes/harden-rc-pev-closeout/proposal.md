# 提案：收紧 requirement-clarify 的 PEV 收口

## 目标

本 change 只保证一条交付不变量：当前产物有对应的、已落盘的 PASS 验证，且 `output/spec.md` 由该验证来源确定性生成。修订后旧 PASS 不再授权交付，重新验证后才能完成；提交、发布或完成中断后可以在原目录重试。

本 change 只修改提案、设计、任务和测试矩阵。暂不修改技能代码、运行时链接或真实业务轮次。

## 现场事实与证据边界

现场重放记录了以下事实：

- **A1–A4（直接事实）**：曾出现手工置 `COMPLETE`、当前产物没有对应 PASS、验证报告迟落或缺失，以及手写 `spec.md` 的情况。
- **A5–A6（直接事实）**：跨轮问题靠 Verifier 自觉追踪；`SKILL.md` 的 assumptions 指令与 state schema 不一致。
- **B1–B3（设计推断或外层事实）**：reopen 的历史投影处理、悬挂轮、未收口 PM 轮等问题在重放中出现或可由代码推断，但不都属于本 change 的核心交付门禁。
- **C（纳入的借鉴）**：借鉴 Nana 脚本化来源绑定、确定性渲染和中断幂等的优点；本 change 只实现当前 PASS、来源一致性和恢复路径所需的最小命令与字段，不引入 Nana 的治理协议。
- **D（外层问题）**：通知传输、外层 runner、工作区其他目录的清理不由 rc 收口证明。
- **E（无法复核）**：没有实测证据证明减少文件或状态会节省 token、提高 ROI，本文不作此类结论。

A4 证明来源一致性值得检查；它不证明需要 companions、洁净树或全局轮次治理。历史验证记录仍保留在 `verification.md`，本提案不把历史记录改写为新版方案的通过证据。

## 保留、删除与延期

| 处理 | 内容 | 理由 |
|---|---|---|
| 保留 | 当轮验证报告落盘并绑定实际 Artifact、有效 Plan 和必要语义输入 | 缺失、错轮或旧 PASS 可能导致错误交付 |
| 保留 | `spec.md` 从已验证来源确定性生成并在完成前复算 | 防止手写输出与验证来源不一致 |
| 保留 | 脚本负责登记、编号、绑定、状态推进、渲染和完成检查 | 这些操作若由模型手写，现场缺口会再次出现 |
| 保留 | 修订使旧 PASS 失效；合法 reopen 与中断恢复可重试 | 保证修订后重新验证，避免重复迭代或误报成功 |
| 保留 | `assumptions` 指令改为写入 schema 已定义的 Evidence Ledger | 修正现有指令与 schema 的直接冲突 |
| 删除 | `SUPERSEDED`、`supersede`、`supersedes` 及工作区全局悬挂轮门禁 | 其他目标的未完成目录不影响当前合法目标；目标路径有歧义时显式选择 |
| 删除 | issue_id 对账与第三次 REVISE 强制 REPLAN/BLOCKED | 不能证明核心交付正确，且会制造流程绕行；Verifier 继续阅读上一轮问题并核查回归 |
| 删除 | companions 哈希清单、轮根漂移扫描、草稿残留和 rc 树洁净门禁 | 伴随文件和草稿不属于唯一交付物 `output/spec.md` |
| 删除 | 固定五个测试文件、74 行矩阵和对应错误码 | 测试从核心行为推导 |
| 延期 | 并发写锁、通知传输、PM 侧同型修复、旧轮清理和迁移 | 不影响本 change 的核心交付不变量 |

## 目标行为

完成前必须同时满足：

1. 当前 `iteration` 有已落盘、编号匹配的 PASS 报告。
2. PASS 绑定的 Artifact、有效 Plan 和语义输入仍与盘上内容一致。
3. `output/spec.md` 由同一组来源生成，重新生成的字节与已发布文件一致。
4. 完成检查通过后，脚本先写完成事件，再复核结果；不能要求预先伪造 `complete` 事件。

普通提示只进入 `warnings`，不统一取消交付动作。普通提示仅包括不影响当前绑定和生成结果的历史投影变化、无关草稿或伴随文件变化；缺报告、REVISE、错轮 PASS、验证输入失配和输出失配属于交付错误。历史投影变化不代表当前输入被篡改；当前交付只依赖当前有效绑定。旧数据可以读取，但缺少有效绑定时不可交付。

## 正常路径

命令只设在模型必须拿主意的地方；下一步已确定的步骤并入同一命令自动做完，模型不执行只改状态或纯机械产出的命令。

1. `init` 选择明确的 rc 目录；同目标已有目录时显式选择继续或新路径，不扫描并阻塞其他目标。
2. `commit plan` 提交计划草稿：脚本原子落盘并登记，推进到 EXECUTING。
3. `commit artifact` 提交产物草稿，草稿 `status` 字段即岔路选择；completed 时脚本自动生成只读验证输入快照并推进 VERIFYING，Verifier 在快照输入上工作。
4. `commit verification` 提交验证报告，报告 `verdict` 字段即岔路选择；PASS 时脚本在同一命令内自动完成绑定复算、确定性渲染 `output/spec.md`、逐字节校验、iteration 上限检查和完成写入。任一步中断，重跑同一命令并复核结果。

## 修订路径

1. 已验证内容发生变化，或用户要求 reopen 时，`reopen` 递增一次 iteration，使旧 PASS 失去当前交付资格。
2. 在同一 rc 目录追加新的 Artifact 或语义输入；旧 Plan 可以复用，但不得改写历史文件。
3. 重新提交 Artifact（自动重做快照）与 PASS 验证报告（自动重做绑定、渲染和完成）。
4. 任何一步中断都从已落盘文件继续，重跑同一命令，不重复增加 iteration。

## 变更规模对比

| 项目 | 原方案 | 精简方案 |
|---|---|---|
| 新状态 | `STOPPED`、`SUPERSEDED` 等治理状态 | 不新增状态；沿用现有流程状态 |
| 新字段 | transitions、companions、supersedes、issue_id、waived_fields 等 | 仅保留当前绑定所需的 provenance，以及完成事件所需的最小 transitions 记录 |
| 命令 | 六个脚本加治理分支和大量 next 动作 | 模型可见入口收敛为 `init`、`commit`（plan/artifact/verification/state-update）、`reopen`、`validate`；`record-provenance`、`render`、`transition`、`complete` 为命令内部零决定步骤 |
| 完成门 | 五条件、洁净树、伴随清单、全局轮次门禁 | 当前 PASS 绑定、来源复算、确定性渲染；先检查再写 complete |
| 测试 | 74 行、五个测试文件 | 按核心路径覆盖缺失、错配、修订和恢复场景 |

## 验收边界

必须覆盖：缺报告、REVISE、错轮 PASS、验证输入被改动时不能交付；当前有效 PASS 可以生成并完成；reopen 后在原目录追加证据并重新验证；PASS 后修改内容必须重新验证；提交、发布、完成中断后可恢复；普通提示、无关草稿和其他目标的未完成目录不阻塞；旧数据可读但无有效绑定不可交付。

没有实测，不声称节省 token、减少调用或提高 ROI。
